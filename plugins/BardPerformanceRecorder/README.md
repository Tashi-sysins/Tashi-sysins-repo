# Bard Performance Recorder

近くのプレイヤーが実際に演奏した音符を、自分の FF14 クライアントで
**観測できる範囲で** 記録し、MIDI ファイルに書き出す Dalamud プラグインです。

## 導入

ゲーム内で `/xlsettings` →「実験的機能」→「カスタムプラグインリポジトリ」に
次の URL を追加すると、`/xlplugins` の一覧に出ます。

```
https://raw.githubusercontent.com/Tashi-sysins/Tashi-sysins-repo/main/repo.json
```

**他のプラグインは必要ありません。** 単独で動きます。
（記録した MIDI を弾き直すときだけ、別途 MidiBard2 などの演奏プラグインが要ります）

## 実機での検証結果（2026-09-21）

`D:\MIDI\ファミマ入店音.mid`（17音・5.5秒・和音あり）を
別キャラに演奏させて記録し、元ファイルと比較した結果：

| 項目 | 結果 |
|---|---|
| 対応がついた音 | **17 / 17（100%）** |
| 不足 | **0音** |
| 余分 | **0音** |
| 音高の並び | **完全に一致** |
| 開始時刻のずれ | **平均 21.0ms**（中央 22.6ms・最大 51.2ms） |
| **音長のずれ** | 比 2.89 倍（和音の曲。単音なら中央 0ms → 下記） |

### 音長について（2026-09-21・制御実験で解明）

パケット内の `0xFE` は「音の終わり（離鍵）」を示しています。
これを使うことで音長を復元できるようになりました。

| 検証した曲 | 音数 | 音長の比 |
|---|---|---|
| **境界連打**（0.16秒間隔・24音） | **24/24** | **1.00倍** |
| **繰り返し**（単音・1秒間隔・8音） | **8/8** | **1.00倍** |
| 音長テスト（単音・6音） | 6/6 | 0.99倍 |
| 和音・速い曲（17音） | 17/17 | 2.89倍（誤差あり） |

**単音なら、密な連打でも音長がほぼ完全に復元できます。**

**ただし `0xFE` は和音では出ません。**
単音なら 0.16 秒間隔の連打でも全音に出ますが、
和音では 17 音に 1 件しか出ませんでした。
「密だから出ない」のではなく「**和音だから出ない**」と分かっています
（制御実験で切り分け済み）。

合図が来ない音は一定時間（既定1秒）で打ち切ります。
この値はトレードオフで、短くすると和音の曲が、
長くすると単音を長く伸ばしたときが正確になります。

ゲームに依存しない部分の自動検証は 115 件すべて通っています。

## できること / できないこと

### 取得できるもの

- 演奏者の識別（EntityId）・名前
- 音符（音高）
- 音色（ギターの音色切替など）
- 合奏時の演奏者ごとの区別
- 演奏者の `Mode` / `ModeParam` の生値（楽器の判定に使う）
- **生パケット全バイト**（解釈前のそのまま）
- **自分が押した鍵**・オクターブ・音色（照合の正解データ）

### 取得できないもの

| 項目 | 代わりにどうするか |
|---|---|
| **音の長さ** | `0xFE`（離鍵の合図）があれば復元できる。無い場合は一定時間で打ち切る（上記参照） |
| **テンポ** | 書き出し基準の BPM（既定 120）を使う。**元曲のテンポではない** |
| **強弱（ベロシティ）** | 全音符を固定値（100）で書き出す |
| **演奏者が実際に弾いた時刻** | パケット受信時刻で代用。通信の遅れぶんずれる |

### 楽器について

楽器は演奏者の `Character.ModeParam` から読みます。
**演奏者が視界内にいて演奏モードに入っているときだけ**取得でき、
取れなかった場合は記録上 `-1` になります。

## ビルド手順

### 必要なもの

- .NET 10 SDK（`dotnet --version` で 10.x であること）
- Dalamud がインストール済みであること
  （`%AppData%\XIVLauncher\addon\Hooks\dev\` が存在すること）

### 手順

```pwsh
cd C:\ソース\BardPerformanceRecorder\BardPerformanceRecorder
dotnet build -c Release
```

出力：`bin\Release\BardPerformanceRecorder.dll`

### 検証を走らせる（ゲーム不要）

```pwsh
cd C:\ソース\BardPerformanceRecorder\BardPerformanceRecorder.Tests
dotnet run -c Release
```

MIDI 変換と記録の状態遷移を、ゲームなしで確認します。
最後に `成功 115 件 / 失敗 0 件` と出れば通っています。

確認している内容：音高・音順・時刻の一致、連続した同音、休符、和音、
演奏者の切り替わり、記録途中の停止、異常値の破棄、番兵バイトの扱い、
書き出し基準 BPM を変えても実時間が保たれること、
パケット受信中に停止しても発音と消音が釣り合うこと。

## まず最初にやること（実機での最初の1回）

**全楽器・全音程を弾かせる必要はありません。** まず「そもそも音が届くか」を確かめます。

### 手順（5分）

1. `/bprec` →「**取得可否**」タブ
   - 「解決できず」と出ていたら、ここで止まりです（README 末尾の項目へ）
2. 「**設定**」タブで次を入れる（既定で入っています）
   - 生パケットを残す
   - 自分が押した鍵を記録する
   - 演奏者を絞らず全部記録する
   - **合奏パケットも記録対象にする** ← 他人の音が合奏側に来る可能性があるため
3. 「記録」タブで **記録を開始**
4. **自分で**演奏モードに入り、ゆっくり単音で10音ほど弾く
   （いちばん低い鍵 → 上がっていく → 同じ鍵を3回 → 少し休む）
5. 別キャラにも同じように弾かせる
6. **記録を停止して書き出し**
7. 「**診断**」タブを見る

### 診断が答えること

- パケットが届いたか（届かないなら、その原因の候補）
- どのバイトが音符らしいか（こちらの読み方が合っているかの裏取り）
- **音高のずらし量が正しいか**（ずれていれば具体的な数値を提案）

自分で弾いた記録があると、「何を弾いたか」が確実に分かるので、
受信データと突き合わせて**自動で**ずれを判定できます。
これが `MidiNoteOffset` を決める一番確実な方法です。

### なぜ全楽器を弾かせなくてよいのか

- 音程の扱いは楽器によって変わりません（パケットに乗る値は同じ）
- 楽器は音符とは別の場所（`ModeParam`）から読んでいます
- いちばん不正確な「音の長さ」は、音程をいくら録っても改善しません

楽器ごとに確かめる価値があるのは**ギターの音色**（0〜4）だけです。

## 使い方

1. `/bprec` で画面を開く
2. 「記録」タブで **記録する演奏者** を選ぶ
   - 演奏モードに入っている近くのプレイヤーが一覧に出ます
   - 「自動」にすると、最初に音を出した人を掴みます
3. **記録を開始**
4. 相手が演奏する
5. **記録を停止して書き出し**

保存先（既定）：`%UserProfile%\Documents\BardPerformanceRecorder\`

出力は最大6つです。

| ファイル | 内容 |
|---|---|
| `performance_日時.mid` | 標準MIDIファイル |
| `performance_日時.txt` | **何を観測して何を推定したかの内訳**、生イベント一覧 |
| `diagnosis_日時.txt` | **自動診断**（読み方が正しいか、音高のずれの判定） |
| `raw_日時.csv` | **生パケット全件**（16進。解釈前のバイト列そのまま） |
| `raw_日時.txt` | 生パケットを人が読める形に並べたもの |
| `localkeys_日時.csv` | 自分が押した鍵の時系列 |

**MIDI が作れなかった場合でも、生ログと診断は必ず保存されます。**
「録れなかった」という事実こそ次の手を決める材料になるためです。

生パケットを残しておく理由は、**こちらの読み方が間違っていても
録り直さずに何度でも読み直せる**ようにするためです。

`.txt` のほうには、音長を推定した個数・暫定長を当てた個数・
破棄したデータ件数・演奏者ID・楽器IDが書かれます。
MIDI だけ見ても推定部分が分からないため、必ず一緒に残してください。

## 元のMIDIと比べる（精度の確認）

記録した MIDI が元の演奏とどれだけ合っているかを、機械的に比べられます。

```pwsh
cd C:\ソース\BardPerformanceRecorder\tools
python -X utf8 compare_midi.py "D:\MIDI\ファミマ入店音.mid" "%USERPROFILE%\Documents\BardPerformanceRecorder\performance_日時.mid"
```

出るもの：

- **対応がついた音の割合**（取りこぼしがないか）
- **不足した音・余分な音**の一覧（分けて数えます）
- **開始時刻のずれ**（平均・中央・95%ile・最大・符号つき）
- **音長のずれ**（同上。長さの比も出ます）

`--verbose` を付けると、音ごとの対応の一覧が出ます。

全体が一定量ずれるのは、記録開始から演奏開始までの待ち時間や
通信の遅れなどが混ざったものです。内訳は分からないので
「開始位置の差」と呼び、それを補正したうえで相対的なずれを見ます。

### このツールについて（v2・2026-09-21）

旧版（`tools\旧版\compare_midi_v1.py`）には次の問題がありました。

| 問題 | 実害（実測） |
|---|---|
| 最初のテンポだけを曲全体に使う | テンポが変わる曲で **20.6%一致・2068音の誤検出**（中身は同じファイル） |
| 音長を比較しない | **音長が半分のファイルを「すべて記録できています」と誤判定** |
| 先頭どうしの差で整列 | 先頭1音が欠けると **不足2・余分1・平均318ms** と誤検出（正解は不足1・ずれ0） |

手持ちの MIDI 540 件のうち **181 件（34%）がテンポ変更を含む**ため、
1つめは実際に問題になります。v2 ではいずれも解消しています
（同じ検証で 100%一致・平均0.3ms、音長は「0.50倍」と正しく検出、
先頭欠落は「不足1・ずれ0.2ms」）。

### 保存済みログから作り直す（録り直し不要）

生パケットを残してあるので、**録音し直さずに**本番と同じ処理へ流し直せます。
記録処理を直したあと、過去の記録で後退がないか確かめるのに使います。

```pwsh
cd C:\ソース\BardPerformanceRecorder\BardPerformanceRecorder.Replay
dotnet run -c Release -- "%USERPROFILE%\Documents\BardPerformanceRecorder\raw_日時.csv"
```

元の受信時刻・順序・重複をそのまま再現します。
**前処理を入れないこと**が大事です。過去に重複を勝手に除いて再生したために、
実機の不具合が隠れて原因を取り違えたことがあります。

## 実機での検証手順

「記録結果と音高・音順・時刻を比較する」ための手順です。
**自分で用意した短い既知の MIDI** を使ってください。

### 準備

1. 10〜20音程度の、音高と順序がはっきり分かる短い MIDI を用意する
   （例：ド→レ→ミ→ファ→ソ を 0.5 秒間隔、同じ音を3回続ける箇所も入れる）
2. 別キャラクター（サブアカウント等）に MidiBard2 などでそれを演奏させる
3. 記録側のキャラクターを**演奏者の近くに立たせる**

### 手順

1. 記録側で `/bprec` → 演奏者を選択 → 記録開始
2. 演奏させる
3. 記録停止 → 書き出し
4. 出力された `.mid` を元の MIDI と並べて比較する

### 確認する点

| 確認項目 | 見るところ |
|---|---|
| **音高が合っているか** | 元 MIDI と記録結果のノート番号。ずれていたら `MidiNoteOffset`（現在24）を調整する |
| **音順が合っているか** | 音の並び順 |
| **時刻が合っているか** | 音と音の間隔。全体が一定量ずれるのは通信遅延なので正常 |
| **連続した同音** | 3回続けた音が3個として残っているか（1個に潰れていないか） |
| **休符** | 無音区間が詰まっていないか |
| **オクターブ** | 演奏者にオクターブを変えてもらい、記録が追従するか |

### 音高の対応（実測で確定済み・2026-09-21）

**基準が 2 つあります。取り違えると 15 半音ずれます。**

| 取得元 | 値の範囲 | C3(MIDI 48) にする補正 | 定数名 |
|---|---|---|---|
| 受信パケットの音符バイト | 24〜60 | **24** | `MidiNoteOffset` |
| 自分の押鍵（照合用） | 39〜75 | **9** | `LocalKeyMidiOffset` |

どちらも 37 個の連番です。パケット側は 24→C3, 36→C4, 48→C5, 60→C6。

ゲーム更新で変わった場合は
`Game\PerformancePackets.cs` の該当の定数を変えてください。
「調査」タブの押鍵履歴と「診断」タブで、実測して確かめられます。

## 既知の制限

- **音長は条件によります。** 単音ならほぼ正確ですが、和音や速い曲では
  離鍵の合図が出ないため誤差が残ります。
- **タイミングは 20〜50ms 程度ずれます。** パケットは約 0.49 秒ごとにしか届かず、
  その区間を 10 スロットに分けた位置（1 スロット ≒ 50ms）までしか分かりません。
- **同じパケットが必ず 2 回届きます。** 同じ内容が続いたら無視する処理を入れています
  （画面の「重複」件数で確認できます）。これを外すと音が増えます。
- **テンポは復元できません。** 書き出しの BPM は基準値でしかありません。
- **強弱は復元できません。** 全音符が同じベロシティになります。
- **観測できるのは自分のクライアントに届いた範囲だけ。**
  距離が離れる・視界から外れるなどで届かなければ記録できません。
- **合奏の記録は試験的。** 構造としては対応していますが、
  最初の対象はソロ演奏です。合奏は実機で未確認です。
- **ゲームの更新でシグネチャが壊れる可能性があります。**（次項）
- 音声参考資料を使った楽器判定・音声からの採譜は**実装していません**
  （設計図どおり後続課題）。

## 送信は一切しません

このプラグインは受信ハンドラを**観測するだけ**です。
ゲームへのパケット送信・演奏操作は実装していません。

## シグネチャが壊れたとき

ゲーム更新後に画面の「取得可否」タブで
「解決できず」と出る場合、シグネチャが通用しなくなっています。

1. `docs/STAGE1.md` に、検証に使った手順（PE を直接バイト列検索し、
   逆アセンブルで裏を取る）を書いてあります。同じ方法で新しいパターンを探せます。
2. 参照元は MidiBard2 の `Midibard\Managers\Offsets.cs` です。
   上流が更新していれば、そちらを先に見てください。
3. シグネチャは `Game\PerformanceSignatures.cs` にまとまっています。

### 設計上の分け方

設計図の指示どおり、**取得処理と変換処理を分けています**。

- `PerformanceHookManager`（フック内）：必要なバイトを写してキューに積むだけ。
  例外は内側で握りつぶし、元の処理は必ず呼びます。
- `PerformanceRecorder`：発音・消音の判定と時刻付け。
  時刻は `Stopwatch`（単調増加時計）で測ります。
- `MidiExporter`：**Dalamud に一切依存しません。**
  そのためゲーム無しで単体検証できます。
