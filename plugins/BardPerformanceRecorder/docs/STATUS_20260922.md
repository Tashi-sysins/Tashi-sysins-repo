## 2. 連続記録「ずっと記録する」（今回の主役）

### 2.1 なぜ作ったか

演奏会では曲が次々に演奏される。曲ごとに開始・停止を押すのは現実的でない。
押しておけば**演奏を待ち、曲ごとに自動で区切って保存する**機能にした。

### 2.2 仕様

```
[ずっと記録する] を押す
   ↓
 待機 ──── パケットが来た ────→ 記録
   ↑                              │
   │                       15秒 途切れた
   │                              │
   └──── 保存して待機に戻る ←─────┘

 待機のまま15分 → 自動終了
```

| 決まり | 既定値 | 設定変更 |
|---|---|---|
| 曲の区切りとみなす無音 | **15秒** | 可（3〜120秒） |
| 待機をあきらめる時間 | **15分** | 可（1〜600分） |

### 2.3 動作中の仕様

- **「全演奏者を記録」を自動でONにする**
  … 連続記録は「その場の演奏を残す」用途。1人に絞ると取りこぼす。
  誰を残すかは後から選び直せる。
- **連続記録中は手動ボタンを隠す**
  … 両方から開始・停止できると、いまどちらの状態か分からなくなる。
- **途中でやめても、記録中の分は保存する**
  … 録れた演奏を捨てないため。
- **録れた曲を画面に一覧**（時刻・音数・人数・ファイル名、最大50件）
  … 回しっぱなしにした後、何が録れたか一目で分かるように。

### 2.4 実装上の判断

判断ロジックを `Recording\ContinuousPolicy.cs` に切り出し、
**ゲームにも画面にも依存させない**構造にした。

理由：「15分待つ」を実機で試すと本当に15分かかる。
境界値（14分59秒 / 15分ちょうど など）を手元で何度でも確かめられるようにした。

検証14件を追加。

## 6. 現在の仕様（まとめ）

### 6.1 記録の方法

| 方法 | 用途 |
|---|---|
| **ずっと記録する** | 演奏会など。押しておけば曲ごとに自動保存 |
| 記録を開始／停止 | 特定の演奏を狙って録る |

### 6.2 出力

停止（または曲の区切り）ごとに、`D:\MIDI\作成Midi\` へ3点セットが出る。

```
performance_日時.mid    MIDI本体（トラック名の先頭に楽器名）
performance_日時.json   MidiBard2用の設定
performance_日時.txt    説明（トラック一覧・推定の内訳・除外した人）
```

生ログ・診断は `~\Documents\BardPerformanceRecorder\` に残る。

- **トラック名は `Horn - Player Name (observed)` 形式**
  MidiBard2 はトラック名から楽器を自動で持ち替えるので、
  読み込むだけで元と同じ編成で弾き直せる。
- **`AssignedCids`（誰が弾くか）は空**
  観測できるのはセッション限りの EntityId で、
  設定ファイルが使う永続 ContentId とは対応付けられないため。
- **ファイル名は重複しない**（既存があれば `_2` `_3`）
- **Dドライブが使えないときは生ログの隣に落とす**（記録を失わせない）

### 6.3 ノイズ対策

近くで無関係な人がソロ演奏していると、その音も混ざる（実測で確認済み）。

**記録は全員ぶん残し、MIDI書き出しのときだけ絞る**方式。

- 画面「演奏者を選んで作り直す」… 実際に届いた人だけが楽器・音数つきで並ぶ
- 別名（`_選択N人`）で保存し、元のファイルは消さない
- **除外した内容は必ず `.txt` に残す**（黙って減らすと取りこぼしと区別がつかない）
- コマンド `--list` / `--only 名前,...` / `--skip 名前,...`（過去ログにも使える）

## 7. 残っている弱点

### 7.1 和音の多い曲では音の長さが不正確

| 条件 | 音長比 |
|---|---|
| 単音 | **1.00倍** |
| 和音の多い曲 | 1.8〜2.9倍 |

和音だと消音の合図（`0xFE`）がほとんど飛んでこないため。
**検証した曲では音程・タイミング・音数・楽器が一致した**ので、
弾き直す用途では実用上の問題が少ない。
ただしこれは試した条件での結果で、全曲を保証するものではない。

### 7.2 原曲と同じトラック構成には戻らない

記録は**演奏者ごとのトラック**になる。
一人が原曲の3トラック分を弾いた場合、1トラックに合流する。
パケットに「どのトラックの音か」という情報が無いため、観測からは分離できない。

### 7.3 その他

- フック内でオブジェクトテーブル走査を行っている（外部レビュー指摘・未対応）
- 安全に読めるバッファ長が未確定
  （セグメントヘッダから読む仕組みは入れたが、その位置にあるかは実機未確認）
- 二重受信の原因（ゲームの再送か二重フックか）が未切り分け

## 8. 【重要】この間に私が起こした事故と教訓

レビュー対応を急いだ結果、**動いていたものを3回壊した**。同じ失敗を防ぐために記録する。

### 8.1 未確認の推測でパケットを捨てて記録が全滅

「セグメントヘッダから長さを読み、短ければ捨てる」処理を安全対策として入れた。
→ **実機のパケットが1件も記録されなくなった**（3回の記録すべて生ログ0行）。

原因：`packet` の16バイト手前がセグメントヘッダという想定が外れており、
そこにあった別の値が「妥当な長さ」に見えて全部 `return` していた。

**教訓：未確認の推測でデータを捨てるのは、安全策ではなく事故。**
長さは**読む量を減らす**のにだけ使い、**捨てる判断には使わない**。

### 8.2 動いているループを削除して1人分しか録れなくなった

生ログが「1人1エントリ・128バイト」に見えたことから
**「1パケット＝1人分」と誤認し、8人分のループを削除**した。
→ **合奏で1人分しか記録されなくなった。**

原因：生ログが1人1エントリなのは、コードが**1人分ずつ別エントリで保存している**から。
同一時刻の8エントリは**1パケットを展開した結果**であって、8個届いていたのではない。

**教訓：生ログの見た目（1件の長さ・件数）は保存側の都合であって、パケット構造ではない。**
構造を判断するなら保存前の生データか逆アセンブルを見る。

**正しい構造（確定）：**
```
[ヘッダ 8B][0x80B × 8人分] = 0x408B
  各枠 +0x00 CharacterId / +0x04 noteCount(60) / +0x05 音符×60 / +0x41 音色×60
```

### 8.3 「2つの形式がある」という誤った仮説

8.2 のバグで8バイトずれて見えたものを「ゲーム側に2種類の形式がある」と誤診断し、
判別処理まで実装した。**ゲーム側は何も変わっていなかった。**

### 8.4 共通する原因

3件とも **実機で確かめずにコードを変えた**こと。
昼の時点で8人合奏が完璧に録れていた以上、元のコードは正しかった。

**ユーザーの「おかしくなってませんか？」が正解だった。**
自分の変更を先に疑うべきだった。

### 8.5 再発防止

レイアウト定数と「1パケットから8人分すべて読める」ことを**自動テストで固定**した。
同じ削除をすれば必ず落ちる。
