## 0. この資料の目的

FF14 の演奏を観測して MIDI 化するプラグインを開発している。
**短いソロ演奏については実用水準に達した**が、
最終目標には届いていない。

### 最終目標

1. **8人が合奏している演奏データを取得し、MIDI を生成できること**
2. **人が多い場所での取得**が前提のため、
   関係ない演奏を除く仕組み（ノイズ対策）が必要

この目標に向けて、**何を作るべきか・どの順で進めるべきか**について
意見をいただきたい。

## 1. 前提となる実測事実

すべて逆アセンブルまたは実機データで確かめた内容。推測ではない。

### 1-1. データの取得経路

- ゲーム内の**パケット受信ディスパッチャ**（`0x1418D9500`）をフックしている
- 引数は `f(a1, sourceId, packet)`、`packet+2` が opcode、ペイロードは `packet+0x10`
- **演奏 opcode は `0x337`**（Dalamud の Network Monitor で実測）
- MidiBard2 由来の個別ハンドラは**実機で一度も呼ばれなかった**ため使っていない

### 1-2. ソロ演奏パケットの構造

```
+00      : 0x0A 固定（スロット数10。音符数ではない）
+01〜+0A : 音符スロット × 10
+0B〜+14 : 音色スロット × 10
```

**10個のスロットは、その約0.49秒のあいだに起きたことを時間順に並べたもの。**
1スロット ≒ 50ms。

| 値 | 意味 |
|---|---|
| 実音（24〜60） | その位置で音が鳴り始めた |
| `0xFE` | その位置で音が終わった（**離鍵**） |
| `0xFF` | 何も起きていない |

連打では `. 0xFE G4 . 0xFE G4 . 0xFE . G4` のように
**離鍵と発音が交互に並ぶ**。

### 1-3. 音高の対応（基準が2つある）

| 取得元 | 値の範囲 | C3(MIDI 48)にする補正 |
|---|---|---|
| 受信パケットの音符バイト | 24〜60 | **24** |
| 自分の押鍵（照合用） | 39〜75 | 9 |

### 1-4. その他の実測値

- パケットは約 **0.49 秒ごと**（最小471ms・最大548ms）
- 同じ内容が **0〜5ms の間隔で2回**届く（ゲーム再送か二重フックかは未切り分け）
- 他人の楽器は `Character.Mode == Performance(16)` のときの `ModeParam`
- **自分の演奏は記録できない**（自分のクライアントに送り返されないため）

## 2. いま「できている」こと

### 2-1. ソロ演奏の記録（実測で確認済み）

制御実験用の MIDI を自作し、別キャラに演奏させて元ファイルと比較した。

| 検証内容 | 音数 | 開始時刻のずれ | 音長の比 |
|---|---|---|---|
| 境界連打（0.16秒間隔・24音） | **24/24** | 中央 25ms | **1.00倍** |
| 繰り返し（単音・1秒間隔・8音） | **8/8** | 中央 17ms | **1.00倍** |
| 音長テスト（0.1〜3.0秒・6音） | **6/6** | 平均 19ms | 0.99倍 |
| 実際の曲・和音あり（17音） | **17/17** | 中央 23ms | 2.89倍 |

- **音高・音順・音数**：取りこぼしゼロ
- **開始時刻**：20〜25ms のずれ（スロット幅50msの半分程度）
- **音長**：単音ならほぼ完全に復元できる

### 2-2. 土台として整っているもの

| 機能 | 内容 |
|---|---|
| 生パケットの保存 | 解釈前のバイト列を全件 CSV に残す。読み方を間違えても録り直し不要 |
| ログ再生 | 保存済みログを**本番と同じ処理**に流せる（`BardPerformanceRecorder.Replay`） |
| 精度比較ツール | 元 MIDI と突き合わせ、不足・余分・開始時刻・音長を数値化（`tools/compare_midi.py`） |
| 制御実験用 MIDI 生成 | 音長・連打・繰り返し・半音階のテスト曲を作る（`tools/make_test_midi.py`） |
| 自動検証 | ゲーム不要の検証 115 件 |
| 演奏者別トラック | MIDI 出力を演奏者ごとに別トラック・別チャンネルに分ける |
| 二重観測の除外 | 同じ内容が 50ms 以内に来たら無視（時間窓方式） |
| 実行中ビルドの表示 | 画面と出力に記録した版を残す |

## 3. いま「できていない」こと

最終目標との差分。**優先度が高い順**に並べている。

### 3-1. 【最重要】合奏パケットを処理していない

**現在の主経路は、ペイロードをソロ形式でしか読んでいない。**

```csharp
// PerformanceHookManager.HandlePerformancePacket
var raw = new byte[PerformanceConstants.SoloPacketSize];   // 24バイト固定
var count = payload[PerformanceConstants.SoloOffsetCount]; // ソロ固定
```

`HandleEnsemble()` という関数は残っているが、
それを呼ぶフック（`EnsembleReceivedHandler`）は実機で発火しないため
**事実上のデッドコード**。

未解明な点：

| 項目 | 状況 |
|---|---|
| 合奏の opcode | **未調査**（`0x337` とは別の可能性が高い） |
| 合奏パケットの構造 | 静的解析では「8人×0x80バイト、各枠に CharacterId + 音符60 + 音色60」と読めたが、**実機データで未確認** |
| 合奏時に `0x337` も流れるか | 未確認 |
| 8人ぶんが1パケットに入るのか、人ごとに別パケットか | 未確認 |

### 3-2. 【最重要】ノイズ対策の仕組みが無い

人が多い場所では、**関係ない人の演奏も同じ opcode で届く**。
現在の絞り込みは次の2つしかない。

- 演奏者を1人だけ選ぶ
- 全員記録する（`RecordAllPerformers`）

**足りないもの：**

| 必要な機能 | 現状 |
|---|---|
| パーティ／アライアンスの人だけ記録 | **無し** |
| 距離で絞る（◯◯メートル以内） | **無し** |
| 演奏者を複数選んで記録（8人まで） | **無し**（1人か全員のみ） |
| 記録中に演奏者が増減したときの扱い | **未検討** |
| 同じ場所の別グループを分けて記録 | **無し** |

なお `Character` から位置は取れるはずだが、**実装していない**。

### 3-3. 和音での音長が不正確

単音なら音長がほぼ完全に取れるが、**和音では `0xFE`（離鍵の合図）がほとんど出ない**。

| 条件 | 元の音符 | `0xFE` の数 |
|---|---|---|
| 単音・0.16秒間隔の連打 | 24 | **24（全音）** |
| 単音・1秒間隔 | 8 | 11 |
| **和音・速い曲** | 17 | **1** |

「密だから出ない」ではなく「**和音だから出ない**」と切り分け済み。
スロットが埋まって合図の余地がなくなると推測しているが、**理由は未確認**。

合図が来ない音は一定時間（既定1秒）で打ち切っているが、
これは**トレードオフ**で、短くすると和音が、長くすると単音が正確になる。

**8人合奏では常に多声になる**ため、この問題は目標に直結する。

### 3-4. 長時間の記録が未検証

検証したのは最長でも 30 秒程度。以下は未確認。

- 数分の記録でメモリがどうなるか（生ログは全件保持している）
- 保存にかかる時間（停止時に同期処理で CSV・テキスト・診断・MIDI を書く）
- 時間のずれが蓄積しないか
- ファイル名が秒単位なので、同じ秒に重なると衝突する

### 3-5. 実装上の未対応（外部レビュー指摘）

以前 Codex にレビューしてもらった際の指摘で、未対応のもの。

| 指摘 | 内容 |
|---|---|
| フック内の作業量 | オブジェクト一覧の走査・配列確保・状態遷移をフック内で行っている |
| バッファ長の検証 | `count` の上限は見ているが、**読み取り可能な長さそのものは検証していない** |
| 取得経路の記録 | ログに「ディスパッチャ経由か個別フック経由か」が残らない |
| 二重観測の原因 | ゲーム再送か二重フックか**未切り分け** |

### 3-6. その他

- **テンポ・強弱**は復元できない（パケットに無い）
- **楽器**は `ModeParam` から読むが、視界外だと取れない
- **音色（ギターのトーン）**は取得しているが、MIDI への反映は未検討

## 4. 相談したいこと

最終目標（8人合奏＋ノイズ対策）に向けて、次の点について意見をいただきたい。

### 4-1. 合奏パケットの調査方針

現在は「合奏中に Network Monitor で opcode を実測する」しか
手がないと考えている。

- もっと確実・効率的な調べ方があるか
- 静的解析で合奏側のディスパッチ分岐を特定する価値はあるか
  （`0x1418D9500` の switch 内に合奏用の分岐があるはず）
- 8人ぶんのデータが1パケットか別パケットかで、設計が変わる。
  先に確かめるべきことの優先順位は

### 4-2. ノイズ対策の設計

人が多い場所で「聴きたい合奏だけ」を取る方法として、
次を考えているが、どれを優先すべきか。

| 案 | 長所 | 短所 |
|---|---|---|
| A. パーティ／アライアンスで絞る | 確実。8人＝アライアンス1つと合致 | 野良の合奏イベントでは使えない |
| B. 距離で絞る | party 外でも使える | 近くに別グループがいると混ざる |
| C. 演奏者を手動で複数選ぶ | 確実 | 事前に誰が弾くか分からないと使えない |
| D. 記録後に選別する | 取りこぼしが無い | 生ログを全部残す必要がある |

**D（全部録ってから選別）が安全**だと考えているが、
その場合にどんな選別条件を用意すべきか。

### 4-3. 和音での音長をどう扱うか

8人合奏では常に多声になるため、
`0xFE` が出ない前提で設計すべきかもしれない。

- 音長の推定方法として、ほかに取れる手がかりはあるか
- 「音長は正確でなくてよい」と割り切る判断はありうるか
  （再演すれば音高と時刻は合う）
- 楽器ごとに音の減衰が違うことを利用できるか

### 4-4. 進める順番

現時点では次の順を考えている。妥当か。

1. 合奏 opcode の実測（これが無いと何も始まらない）
2. 合奏パケットの構造を生ログで確認
3. 8人ぶんを演奏者別に振り分けて MIDI 化
4. ノイズ対策（絞り込み条件）の実装
5. 長時間記録の検証
6. フック内の安全性（レビュー指摘）

ただし **6 のバッファ長検証は安全性に関わる**ので、
もっと早い段階でやるべきかもしれない。

### 設計上の約束

- **取得と変換を分離**：フック内はコピーとキュー追加のみを目指す
  （現状は一部それを超えている。3-5 参照）
- **`MidiExporter` は Dalamud に依存しない**：ゲーム無しで検証できる
- **生パケットを必ず残す**：解釈を間違えても録り直さずに済む
- **送信は一切しない**：受信の観測のみ
