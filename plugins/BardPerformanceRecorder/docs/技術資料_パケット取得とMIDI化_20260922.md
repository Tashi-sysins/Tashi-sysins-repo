## 1. 何をするプラグインか

FF14 の**他人の楽器演奏を、通信パケットの段階で横取りして MIDI ファイルに復元する**
Dalamud プラグイン。自作。MidiBard2 とは別の独立したプラグインである。

```
他プレイヤーが演奏
      ↓ （サーバーから演奏パケットが届く）
自分のクライアント ──[ここをフックする]──→ ゲームの音が鳴る処理
      ↓
   生バイトを記録
      ↓
   時刻・音高を復元
      ↓
  performance_日時.mid  ＋ .json ＋ .txt
```

### なぜ可能なのか

FF14 では、近くのプレイヤーが楽器を弾くと**その音符データが自分のクライアントに送られてくる**。
そうでなければ自分の耳に演奏が聞こえない。つまり「聞こえている＝データは手元に届いている」。
このプラグインは、そのデータが音になる直前で内容を写し取っている。

**逆に言えば、自分自身の演奏は記録できない。** 自分の弾いた音は自分に送り返されないため。
（記録したい場合は、観測役と演奏役でキャラクターを分ける必要がある）

## 2. 現状：どこまでできているか

### 2.1 達成済み（実機で確認したもの）

| 項目 | 実測結果 |
|---|---|
| **8人合奏の記録** | 全員ぶん取りこぼしゼロ（24/24 音・音長比 1.00） |
| **長時間の記録** | 最長 300秒・5,204音 |
| **無人での連続記録** | 10曲・29,576音を自動で区切って保存（実演で稼働） |
| **楽器の判別** | **28 / 28 種類すべて**（打楽器・エレキ含む） |
| **音高の正確さ** | 全37鍵（C3〜C6）で元MIDIと完全一致 |
| **タイミング** | 開始時刻の中央値ずれ 9.4〜12.0ms |
| **音長（単音）** | 比 **1.00倍** |
| **ノイズ除去** | 無関係な演奏者を書き出し時に除外（録り直し不要） |

### 2.2 できないこと（原理的な限界）

パケットに情報そのものが存在しないため、**実装では解決できない**。

| 項目 | 理由 |
|---|---|
| **テンポ** | パケットに無い。出力の BPM は「実時間を写すための基準値」でしかない |
| **強弱（ベロシティ）** | パケットに無い。固定値で出力 |
| **原曲のトラック構成** | 「どのトラックの音か」がパケットに無い。演奏者ごとの分離が限界 |
| **自分の演奏** | 自分には送り返されない |

### 2.3 精度が落ちる条件（実装上の弱点）

| 条件 | 音長比 |
|---|---|
| 単音（8人合奏でも） | **1.00倍**（正確） |
| 和音の多い曲 | **1.8〜2.9倍**（長くなる） |

理由は6.3節で述べる離鍵マーカー `0xFE` が、和音では飛んでこないため。
**音程・タイミング・音数・楽器はどちらの条件でも正確**なので、弾き直す用途には実用になる。

## 3. 取得経路の特定 ── どうやってフック先を見つけたか

ここが最も難航した部分であり、**アプローチを2回変えている**。

### 3.1 第1の方法：既存プロジェクトのシグネチャを検証（静的解析）

先行する MidiBard2（akira0245・AGPL-3.0）が、演奏パケットの受信関数の
バイト列パターン（シグネチャ）を持っていた。ただし**数年前のもので、現行版で生きている保証がない**。

そこで**ゲームを起動せずに実行ファイルを直接調べた**。

```
1. ffxiv_dx11.exe の PE ヘッダを読み、.text セクションを特定
2. 各シグネチャをマスク付きでバイト列検索
3. ヒットした関数を capstone で逆アセンブル
4. 引数の使われ方・構造体オフセットをアセンブリから読み取る
```

**シグネチャが当たっただけでは同じ関数とは言えない**ため、必ず逆アセンブルして裏を取った。

| シグネチャ | 結果 | アドレス |
|---|---|---|
| `SoloReceivedHandler` | 一意にヒット | `0x140B4E7F0` |
| `EnsembleReceivedHandler` | 一意にヒット | `0x140B4E860` |
| `ChangeOctave` / `SetOption` | **見つからない** | （送信側なので記録には無関係） |

補強材料として、Solo と Ensemble は `0x70` しか離れていない**隣接した兄弟関数**だった。
偶然同じバイト列に当たったのではないと判断できる。

逆アセンブルで読み取った実際のコード：

```asm
; ソロ受信の内側 (0x141967BF0)
movzx eax, byte ptr [rdi]           ; offset 0      = 音符数
cmp   al, 0Ah                       ;   上限 10
movzx eax, byte ptr [rcx+rdi+1]     ; offset 1..10  = 音符番号
movzx eax, byte ptr [rcx+rdi+0Bh]   ; offset 11..20 = 音色
```

→ **旧構造体の定義が現行でもそのまま有効**と確認できた。

### 3.2 【挫折】フックが1度も呼ばれない

実機に入れたところ、**155秒間でフックが0回しか発火しなかった**。

原因を切り分けるため、さらに逆アセンブルして**呼び出し元を特定**した：

- Solo = `0x1418DD2B1`、Ensemble = `0x1418DD2C2` の**1箇所ずつだけ**
- そこは **opcode ごとの巨大な switch 文**で、各分岐が `jmp 0x1418DD954`（共通出口）で終わる典型形
- 第2引数は `lea rdx,[rdi+0x10]` ＝ **IPCヘッダ16バイトの直後**（こちらの実装と一致）

→ **関数もフック対象も正しい。そのopcodeのパケットが届いていない**というのが結論。

### 3.3 突破口：Network Monitor で opcode を実測

Dalamud 内蔵の **Network Monitor**（`/xldata` → Network Monitor → Track ZoneDown）を使い、
他キャラが演奏している最中の通信を直接観察した。

結果：**opcode `0x337`（823）が毎秒2回、送り元＝演奏者の EntityId で連続受信**されていた。

※ 以前使われていた `IGameNetwork` API は廃止済みのため、内蔵ウィジェットを使う必要がある。

### 3.4 第2の方法：ディスパッチャを独自に特定（採用した方式）

個別ハンドラが呼ばれない以上、**全 opcode が必ず通る入口**をフックする方式に切り替えた。

ここで効いたのが **.pdata（例外テーブル）からの関数特定**である。

> **手法の教訓**：switch のジャンプテーブルの境界を推測で割り出そうとすると失敗する
> （範囲が overlap する）。**.pdata から関数範囲を引くのが確実で速い。**

```
共通出口 0x1418DD954 を含む関数 = 0x1418D9500（サイズ 0x528C）
```

入口の命令から引数が判明した：

```asm
movzx r13d, [r8+2]    ; opcode   ← パケット先頭 +2
mov   r14d, edx       ; sourceId
                      ; r8 = パケット先頭
```

→ `f(IntPtr a1, uint sourceId, IntPtr packet)`、**packet+2 が opcode**、**ペイロードは +0x10**

最終的なシグネチャ（[PerformanceSignatures.cs](../BardPerformanceRecorder/Game/PerformanceSignatures.cs) に実装）：

```
48 89 5C 24 20 55 56 57 41 54 41 55 41 56 41 57 48 8D AC 24 ?? ?? ?? ?? B8 70 3C 00 00
```

末尾の `B8 70 3C 00 00`（スタックサイズ 0x3C70）を含めないと3件ヒットして絞れなかった。

**この方式で実機での受信に成功**（ディスパッチャ通過129回のうち72件が演奏パケット）。

### 3.5 なお個別ハンドラも無駄ではなかった

後日判明したことだが、**2人以上が合奏すると `EnsembleReceivedHandler` は実際に発火する**。
「デッドコードだ」という当初の判断は誤りだった。現在は3つとも仕掛けてある。

## 4. パケットの構造（実測で確定した値）

### 4.1 ソロ演奏（24バイト）

```
+00      : 0x0A 固定 ← スロット数10。「音符数」ではない
+01〜+0A : 音符スロット × 10
+0B〜+14 : 音色スロット × 10
+15〜    : 0 埋め
```

### 4.2 合奏（0x408 = 1032バイト）

**1つのパケットに8人分が入っている。**

```
[ヘッダ 8B][0x80B × 8人分]
  各枠 +0x00 CharacterId  (空き枠は 0xE0000000)
       +0x04 noteCount    (60固定)
       +0x05 音符 × 60
       +0x41 音色 × 60
```

### 4.3 ソロと合奏の比較（実測）

| | ソロ | 合奏 |
|---|---|---|
| 長さ | 24 B | **1032 B**（8人分） |
| スロット数 | 10 | **60**（1人あたり） |
| 受信間隔 | **約0.49秒** | **約3.0秒** |
| 1スロットの時間 | 50ms | **50ms（同じ）** |

**スロット間隔が同じなので、時刻復元の処理を共通化できる。**

### 4.4 番兵バイト（最重要）

| 値 | 意味 |
|---|---|
| `0xFF` | そのスロットでは何も起きていない |
| `0xFE` | **そのスロット位置で音が終わった（離鍵）** |

`0xFE` の意味は当初「保持」と誤解していた。6.3節で詳述する。

### 4.5 音高の対応 ── 取り違えると15半音ずれる

**押鍵とパケットで基準が違う。** ここは実際に取り違えて音が15個欠落した箇所である。

| 取得元 | 値の範囲 | C3(MIDI 48) にする加算値 | 定数名 |
|---|---|---|---|
| 自分の押鍵（AgentPerformance +0x60） | 39〜75 | **+9** | `LocalKeyMidiOffset` |
| **受信パケット（音符バイト）** | **24〜60** | **+24** | **`MidiNoteOffset`** |

どちらも37個の連番。パケット側は `24→C3, 36→C4, 48→C5, 60→C6`。
実データで検算し、37音すべてが C3〜C6 の連番になることを確認済み。

### 4.6 楽器の取得（パケット外）

**楽器はパケットに入っていない。** 別経路で読む。

| フィールド | オフセット | 内容 |
|---|---|---|
| `Character.EntityId` | `0x78` | 受信ハンドラの `sourceId` と同じID ← 突き合わせに使う |
| `Character.Mode` | `0x2364` | `Performance`(=16) なら演奏中 |
| `Character.ModeParam` | `0x2365` | 演奏中のとき **Perform シートの行ID（＝楽器）** |

MidiBard2 が使う `PerformanceStructPtr` は**自分専用**で他人には使えない。
また FFXIVClientStructs には演奏パケットの型が存在しないため、**フックが唯一の手段**である。

**制約**：視界外・演奏モード外だと楽器が取れない（その場合 `-1` を記録し、黙って省かない）。

## 5. フック内で何をするか

**フックはゲームの処理の途中に割り込む。ここで重い処理をするとゲームが止まる。**

そのため、フック内でやることは次の3つだけに限定している
（[PerformanceHookManager.cs](../BardPerformanceRecorder/Game/PerformanceHookManager.cs)）：

1. **生バイトを固定長バッファへ写す**
2. **キューに積む**
3. **必ず元の処理を呼ぶ**（ゲームを壊さないため）

例外はすべて内側で握りつぶす。ファイル保存や MIDI 変換は別のタイミングで行う。

### 5.1 読み取り長の問題（未解決）

**ディスパッチャの引数に「パケットの長さ」は渡されていない**（逆アセンブルで確認）。
直接の `call` も0件（関数ポインタ経由）のため、呼び出し側からも辿れない。

FF14 のパケットは `[セグメントヘッダ16B][IPCヘッダ16B][ペイロード]` で、
セグメントヘッダ +0 が全体長になる（出典：https://xiv.dev/network/packet-structure ）。
ディスパッチャが渡すのは IPC ヘッダ先頭なので、16バイト手前を読めば長さが分かる**はず**。

**しかしこれは実機で裏が取れていない。**
そのため長さは「**読む量を減らす**」のにだけ使い、**捨てる判断には使わない**（次節）。

## 6. パケットから MIDI へ ── 時刻と音長の復元

ここがこのプラグインの核心であり、**実測による発見が最も多かった部分**である。

### 6.1 第1段階：スロット位置は時間位置を表す

当初は「パケットが届いた時刻＝音の時刻」としていた。しかし受信間隔が約0.49秒あるため、
**すべての音が0.49秒刻みに量子化されてしまう**。

実データと元MIDIを突き合わせて分かったこと：

> **10個のスロットは、その0.5秒区間内のどの位置で弾かれたかを表す。**

スロット1が F#4(0.000s)、スロット8が D4(0.341s) ──というように順序が完全に一致した。

```
発音時刻 = 受信時刻 + スロット番号 × 50ms
        （50ms = 受信間隔490ms ÷ 10スロット）
```

**実測でタイミングずれが 179ms → 51ms に改善**（最大346ms→106ms）。

**注意**：消音にも同じ基準を適用しないと「消音が発音より前」になって対応が崩れる。
そのため `sounding` を `Dictionary<音高, スロット位置>` として保持している。

### 6.2 スロットの位置自体に意味はない

スロットの**位置は毎回変わる**（リングバッファ的）。単音でも毎回違うスロットに入る。
「どの値が現れたか」と「何番目か（＝時間位置）」だけを見ればよい。

### 6.3 第2段階：`0xFE` は「保持」ではなく「離鍵」だった

**これが音長の精度を決定づけた発見である。**

当初 `0xFE` を「保持」と解釈し、単に発音から除外していた。その結果、
音長は受信間隔に量子化され、**元 0.341〜1.364秒 が 0.349〜0.548秒に潰れていた**
（中央 154ms ずれ・比 1.39倍）。

そこで**制御実験用の MIDI を自作**（`tools\make_test_midi.py`）し、
同じ音を 0.1/0.25/0.5/1.0/2.0/3.0 秒だけ保持させて記録した。

結果：**実音のスロット位置と `0xFE` のスロット位置の差 ＝ 元の音長**（誤差最大27ms）

| 元の音長 | 実音→0xFE の間隔 |
|---|---|
| 0.5秒 | 0.482秒 |
| 1.0秒 | 0.973秒 |
| 2.0秒 | 2.011秒 |
| 3.0秒 | **3.001秒** |

長い音はパケットをまたいで**同じスロット位置**に、短い音は同一パケットの後ろのスロットに現れる。

### 6.4 `0xFE` は和音では出ない（切り分け済み）

「密に弾くと出ないのでは」という仮説を立てたが、**間隔の密さは無関係だった**。

| 条件 | 音符数 | 0xFE の数 |
|---|---|---|
| **単音・0.16秒間隔の連打** | 24 | **24（全音）** |
| 単音・1秒間隔 | 8 | 11（ほぼ全音） |
| **和音・速い曲** | 17 | **1（ほぼ出ない）** |

0.16秒間隔の密な連打でも全音に出たので、**「和音だから出ない」が正しい**。
和音ではスロットが埋まって合図の余地がない、と推測している（理由自体は未確認）。

合図が来ない音は `NoteOffWaitMs`（既定1000ms）で打ち切る。
**短くする＝和音が正確／長くする＝単音が正確**のトレードオフで、両立しない。

### 6.5 第3段階：パケットはスロット順の「イベント列」

連打時のスロットを見ると、次のように並んでいた：

```
.  0xFE  G4  .  0xFE  G4  .  0xFE  .  G4
   閉じる 鳴らす  閉じる 鳴らす  閉じる  鳴らす
```

当初は「先に全部の消音を処理 → 後で全部の発音」の2段階だったため、
余った `0xFE` が別の音を巻き込んで閉じ、**音が欠落した**（C境界連打で 23/24）。

→ **スロットを先頭から1回だけ走査し、`0xFE` なら閉じる・実音なら鳴らす**方式に書き換えた。

| 検証 | 音数 | 音長の比 |
|---|---|---|
| C境界連打（0.16秒×24音） | **24/24** | **1.00倍** |
| B繰り返し（8音） | **8/8** | **1.00倍** |
| D音長（6音） | 6/6 | 0.99倍 |

**どの音を閉じるか**も実測で決めた。「いちばん古い音」ではなく
**「直前に鳴らした音」**が正しい（`CloseNewestFirst`・既定 true）。
実測でスロット9,16,24に音・23と52に0xFE があったとき、直前規則なら元と一致した。
→ **音長ずれ 2523ms→52ms、比 6.13→1.04倍**。

### 6.6 【重要な罠】全パケットが二重に届く

**実機では同じパケットが必ず2回届く**（実測：32件中10種類が重複）。
そのまま処理すると、1回目で鳴らした音が2回目に「同パケット内の繰り返し」と誤判定され**音が増える**。

判定基準は「内容が同じ」だけでは足りない。同じフレーズが繰り返される曲では、
別区間の正当な演奏でも配列が一致してしまうため。実測では間隔が**二極化**していた：

| | 間隔 |
|---|---|
| 二重観測 | **0.0〜5.0ms**（16件） |
| 別の区間 | **461〜535ms**（4件） |

あいだの値は現れない。そこで **50ms の時間窓**を条件に加えた（`DuplicateWindowMs`）。

> **この不具合の切り分けに最も時間を要した。**
> 原因は「生ログを重複除去して再生」していたこと。再生では正しく動くのに実機では音が増える、
> という食い違いが生じた。**実機の挙動を再現するときは、前処理を勝手に入れてはいけない。**

## 7. MIDI ファイルの組み立て

[MidiExporter.cs](../BardPerformanceRecorder/Midi/MidiExporter.cs)（776行）で行う。

### 7.1 イベントの対応付け

```
実時間(ms) → tick 換算：  ticksPerMs = TPQN / (60000 / BPM)
                          既定 TPQN=480, BPM=120 → 1ms = 0.96tick
```

> **教訓**：tick 換算を暗算で間違えた経験があるため、以後は自分で検算せず
> `TimeAs<MetricTimeSpan>` で**実時間に戻して**検証する形にしている。

発音と消音の組は **`(演奏者, 音高)` をキー**にしたキューで対応付ける。
音高だけにすると、2人が同じ音を重ねたとき音長が入れ替わる（実測で 0.2/1.0秒 → 0.4/0.8秒）。

並べ替えの規則は「①時刻順 ②同時刻なら発音を先に」。
スロット位置を反映すると発音が受信時刻より後ろへずれ、前後が入れ替わることがあるため。

### 7.2 演奏者ごとにトラック・チャンネルを分ける

**MIDI は同一チャンネルで同じ音高が重なると読み戻せない。**
対応付けを直すだけでは不十分で、トラック分離まで必要だった。
チャンネル9（打楽器）は避け、16人を超えたら巡回させる。

### 7.3 テンポは専用トラックに分ける

テンポは**元の曲の値ではなく「実時間を写すための基準」**であり、その旨をファイル内にも記している。

> **実際に11件で発生した罠**：テンポ情報を先頭の演奏者トラックに混ぜていたため、
> **演奏者が1人のときだけ**書き出し側がテンポを別トラックへ切り出し、
> トラック名もそちらへ付いて**音符トラックが無名**になった。4人のときは起きない。
> → テンポ専用トラックを最初から分けて解決。

### 7.4 出力される3点セット

`D:\MIDI\作成Midi\` に出力される。

```
performance_日時.mid    MIDI本体（トラック名の先頭に楽器名）
performance_日時.json   MidiBard2 用の設定ファイル
performance_日時.txt    説明（トラック一覧・推定の内訳・除外した演奏者）
```

- トラック名は `Horn - Player Name (observed)` 形式。
  **MidiBard2 はトラック名から楽器を自動で持ち替えるので、読み込むだけで同じ編成で弾き直せる。**
- 楽器が引けないときも `Instrument99` / `UnknownInstrument` と書き、**黙って省かない**。
- `AssignedCids`（誰が弾くか）は**空**。観測できるのはセッション限りの EntityId で、
  設定ファイルが使う永続 ContentId とは対応付けられないため。
- ファイル名は重複しない（既存があれば `_2` `_3`）。**生ログ側と MIDI 側の両方を見る。**
- D ドライブが使えないときは生ログの隣へ落とす（**記録を失わせないため**）。

## 8. 【本題】情報取得（ログ）をどこまで取ったか

**この章がご依頼の中心である。**

### 8.1 基本方針：解釈する前に、生バイトを全部残す

```
こちらの解釈（オフセット・番兵の意味）が間違っていた場合、
解釈後のデータしか残っていないと、実機で録り直すしかない。
生バイトさえ残っていれば、あとから何度でも読み直せる。
```

この方針は**実際に3回救われている**（`0xFE` の意味の訂正、音高オフセットの訂正、
8バイトずれログの救済）。いずれも録り直さずに過去のログから再解析できた。

**サイズ検証で弾いたパケットも生では残す。** 捨てると原因が追えなくなるため。
むしろ**弾かれたパケットこそ「読み方が違う」手がかり**になる。

### 8.2 取得しているログの種類（4系統）

| 系統 | ファイル | 内容 |
|---|---|---|
| **① 生パケット（CSV）** | `raw_日時.csv` | 全バイトを16進文字列で。機械処理用 |
| **① 生パケット（可読）** | `raw_日時.txt` | 16進＋10進を並べた人間用ダンプ |
| **② 自動診断** | `diagnosis_日時.txt` | バイトごとの統計から「音符らしい位置」を自動判定 |
| **③ 自分の押鍵** | `localkeys_日時.csv` | 自分が押した鍵の時系列＝**照合の正解データ** |
| **④ 完成品＋注記** | `performance_日時.txt` | 推定の内訳・除外した演奏者 |

保存先：

| 種類 | 場所 |
|---|---|
| 生ログ・診断 | `%USERPROFILE%\Documents\BardPerformanceRecorder\` |

### 8.3 実際に取得した総量（2026-09-22 時点の実測）

```

  diagnosis_*   58 ファイル

```

**生パケットの内訳（`raw_*.csv` 全50件を集計）：**

| 項目 | 実測値 |
|---|---|
| **パケット総行数** | **9,227 行** |
| うち合奏 | **7,831 行**（84.9%） |
| うちソロ | **1,396 行**（15.1%） |

※ 合奏は1人分（0x80バイト）を1行として保存するため、8人合奏では1パケットが8行になる。
　 **この「見た目の件数」を実際の受信数と取り違えたことが、後述の事故8.6-②の原因である。**

### 8.4 生パケットログの中身（実例）

**CSV（機械処理用）** ── 1行 = 1パケット（合奏は1人分）

```csv
seconds,kind,source_id,performer,mode,mode_param,instrument,byte_count,bytes_hex
```

解釈した値ではなく、**受信時点の周辺情報も一緒に残す**のがポイント：
`mode` / `mode_param` は**演奏モードでないと判定された場合でも生値をそのまま**記録する。
「演奏中でない」という判定自体が誤っていた場合に、あとから気づけるようにするため。

**可読ダンプ（人間用）** ── 16バイトずつ、16進と10進を並べる

```
[   1.2340s] ENS src=0x10021A57 mode=16 param=5 inst=5 len=128
    +000  0A FF FF 24 FF FE FF FF ...   |  10   .   .  36   .   -   .   .
```

10進を併記しているのは、**音符の値は10進のほうが当たりをつけやすい**ため
（`0xFF` は `.`、`0xFE` は `-` で表示）。

### 8.5 自動診断ログ ── データ自身に答えさせる

**16進を人間が睨んで当たりをつける作業を減らす**ために作った
（[CalibrationAnalyzer.cs](../BardPerformanceRecorder/Recording/CalibrationAnalyzer.cs)）。

各バイト位置について「値の種類数・0xFF率・0xFE率・最小/最大」を集計し、
**音符らしく動くバイト位置を自動で指摘する**。

実際の出力（`diagnosis_20260922_033009.txt`・8人合奏808件）：

```
■ 受信したパケット
  ソロ受信 : 0 件
  合奏受信 : 808 件

■ 送り元
  0x10021A57     101 件  演奏者A
  0x10030B74     101 件  演奏者B
  （…8人が各101件＝完全に均等）

■ バイトごとの動き（合奏・全 808 件）
   位置  種類数  0xFF率  0xFE率  最小 最大  判定
   +  0      8      0%      0%   35  188
   +  4      1      0%      0%   60   60        ← noteCount 固定値60
   +  5     20     89%      4%   29   59  ★音符らしい
   +  6     17     90%      5%   26   59  ★音符らしい
   （…+0x05 から連続して★が並ぶ＝想定オフセットと一致）
```

**読み取れること**：
- 8人が各101件と**完全に均等** → 取りこぼしが無い
- `+0x05` から★が連続 → **想定した音符オフセットが正しい**
- 値域 26〜59 が C3〜C6 の範囲に収まる → 音高オフセットが正しい

さらに、**自分の押鍵ログと突き合わせて `MidiNoteOffset` のずれを数値で提案する**機能もある。

#### 診断機能そのもののバグも、診断で見つかった

`CalibrationAnalyzer` は当初**パケット全バイト**を走査しており、
音符数・音色・0埋めまで「音符」と数えて本物の差を埋もれさせていた（合成データで検出）。
→ 音符域だけを見るよう修正。

加えて「音符はここ」という**前提自体が誤っていた場合に気づける**よう、
押鍵値が実際に現れたバイト位置を**総当たりで数えて併記**する機能を追加した。

### 8.6 【重要】ログの設計で実際に起きた3件の事故

**すべて「未確認の推測でデータを捨てた／減らした」ことが原因**である。

#### ① 推測でパケットを捨てて記録が全滅

安全対策のつもりで「セグメントヘッダから長さを読み、短ければ捨てる」処理を入れた。
→ **実機のパケットが1件も記録されなくなった**（3回の記録すべて生ログ 0 行）。

原因：`packet` の16バイト手前がセグメントヘッダという想定が外れており、
そこにあった別の値が「妥当な長さ」に見えて全部 `return` していた。

> **教訓：未確認の推測でデータを捨てるのは、安全策ではなく事故。**
> 長さは**読む量を減らす**のにだけ使い、**捨てる判断には使わない**。
> 想定と違うときこそ生ログが要るので、疑わしいときほど多めに残す。

同じ理由で `CharacterId` 不一致も「捨てる」→「**数えるだけ**」に変更した。

#### ② 生ログの見た目を構造と取り違えてループを削除

生ログが「1人1エントリ・128バイト」に見えたことから
**「1パケット＝1人分」と誤認し、8人分のループを削除**した。
→ **合奏で1人分しか記録されなくなった。**

原因：生ログが1人1エントリなのは、コードが**1人分ずつ別エントリで保存している**から。
同一時刻の8エントリは**1パケットを展開した結果**であって、8個届いていたのではない。

> **教訓：生ログの見た目（1件の長さ・件数）は保存側の都合であって、パケット構造ではない。**
> 構造を判断するなら保存前の生データか逆アセンブルを見る。

#### ③ ②のバグを「ゲーム側に2形式ある」と誤診断

②で8バイトずれて見えたものを「形式が2種類ある」と誤診断し、判別処理まで実装した。
**ゲーム側は何も変わっていなかった。**

#### 共通する原因と再発防止

3件とも **実機で確かめずにコードを変えた**こと。
昼の時点で8人合奏が完璧に録れていた以上、元のコードは正しかった。

→ レイアウト定数と「1パケットから8人分すべて読める」ことを**自動テストで固定**した
（`EnsemblePacketSize==0x408` / `EnsembleMemberCount==8` / `EnsembleOffsetMembers==8`）。
同じ削除をすれば必ずテストが落ちる。

**副産物**：不具合中に8バイトずれて保存された生ログ3件も、
`LooksLikeEnsembleBody()` で位置を判別して読めるようにし、救済済み（各7音）。
**生で残していたから救えた。**

### 8.7 ログを「読み直す」仕組み ── Replay

生ログを残すだけでは足りない。**本番と同じ処理で読み直せる入口**が要る。

`BardPerformanceRecorder.Replay`（436行）が生ログを読み、`FeedAt(時刻, ...)` で
**元の時刻・順序・重複をそのまま**流し込む。

これにより：
- 解釈を変えたとき、**録り直さずに過去50件すべてを再処理して検証できる**
- 「後退していないか」を過去データ全件で確認できる（実際に7件で確認した）
- 演奏者の絞り込み（`--list` / `--only` / `--skip`）を過去ログにも適用できる

> **注意（6.6節の再掲）**：再生時に重複除去などの前処理を勝手に入れると、
> 実機と挙動が食い違って切り分け不能になる。**生のまま流すこと。**

### 8.8 ログ設計の原則（まとめ）

| 原則 | 理由 |
|---|---|
| **解釈前の生バイトを必ず残す** | 読み方の誤りを録り直さずに正せる |
| **弾いたパケットも残す** | 弾かれた理由こそ手がかり |
| **判定が付かない値も生値で残す** | 判定自体が誤っていた場合に気づける |
| **捨てた内容は必ず記録する** | 黙って減らすと取りこぼしと区別がつかない |
| **推測で捨てない・減らさない** | 事故①の教訓 |
| **本番と同じ経路で再生できる入口を持つ** | 検証を実機に依存させない |
| **MIDI が作れなくても生ログと診断は必ず出す** | 失敗時こそ情報が要る |

### 8.9 取得量の上限と保護

- `RawPacketLog.Capacity` = **200,000件**（超過分は件数だけ数えて捨て、`OverflowCount` に出す）
- 可読ダンプは先頭 **2,000件**まで（全件は CSV を参照する旨を明記）
- **実測での最大は809行**なので、上限に達したことはない

### 9.2 残る量子化誤差

スロット位置を使っても **±50ms 程度の量子化誤差**は残る（スロット幅が50msのため）。

### 9.3 ノイズの実態

**近くで無関係な人がソロ演奏していると、その音も混ざる**（実測で確認）。
合奏していない別々の3人がソロで弾いた演奏が、すべて同じ記録に入った。
**「パーティ内限定」という推測は誤りだった。**

それ以前の記録で混入ゼロだったのは、たまたま近くで誰も弾いていなかっただけ。
（聴衆はパケットを送らないので、人が見に来ても記録には影響しない）

**対策**：記録は常に全員ぶん残し、**MIDI 書き出しのときだけ絞る**（録り直し不要・何度でもやり直せる）。
除外した内容は必ず `.txt` に残す。

### 9.4 比較ツールの精度（検証する側の検証）

`tools\compare_midi.py`。**旧版の実害を実測してから作り直した**（旧版は `tools\旧版\` に保全）。

| 旧版の問題 | 実害 |
|---|---|
| 最初のテンポだけ使う | テンポ変更曲で **20.6%一致・2,068音を誤検出**（中身は同じファイル） |
| 音長を見ない | **音長が半分でも「すべて記録できています」と誤判定** |
| 先頭どうしで整列 | 先頭1音欠けで不足2・余分1・318ms誤検出（正解は不足1・ずれ0） |

手持ちMIDI 540件中 **181件(34%) がテンポ変更を含む**ので、1つめは実害があった。

さらに「演奏者を区別せず対応付けるため、2人が同じ音高を同時に弾くと取り違える」欠陥も修正
（音長のずれが実際は0なのに700msと誤表示 → 0ms）。

### 9.5 比較時の注意：AdaptNotes による移調

FF14 の音域（C3〜C6）外の音は MidiBard2 が**1オクターブ移動して**演奏する。
記録はその「実際に鳴った音」を正しく写すので、原曲と直接比べると不一致になる。

（例：徹子の部屋 285音中64音が移調 → そのまま比較 77.5%、移調を反映すると 95.8%）

## 10. 連続記録（無人運用）

演奏会では曲が次々に演奏されるため、曲ごとに開始・停止を押すのは現実的でない。

```
[ずっと記録する] を押す
   ↓
 待機 ──── パケットが来た ────→ 記録
   ↑                              │
   │                       15秒 途切れた
   │                              │
   └──── 保存して待機に戻る ←─────┘

 待機のまま15分 → 自動終了
```

**設計のキモ**：判断ロジックを [ContinuousPolicy.cs](../BardPerformanceRecorder/Recording/ContinuousPolicy.cs)
に切り出し、**ゲームにも画面にも依存させない**。
でないと「15分待つ」を実機でしか試せない。境界値（14分59秒/15分ちょうど 等）の検証14件を追加した。

### 実証：2026-09-22 03:00〜03:37 に無人で10曲を自動記録

**3つの別グループが交互に演奏する場**で、8人合奏×9曲＋ソロ1曲、計 **29,576音**。

| | 値 |
|---|---|
| 曲中の最大無音 | **3.3〜7.3秒**（合奏パケットの間隔そのもの） |
| 曲と曲の間隔 | **13〜39秒** |
| 最長の1曲 | **300秒・5,204音** |

**曲中に15秒を超える無音は一度も無く、ぶつ切りゼロ・つながりゼロ。**
グループが入れ替わっても、グループごとに別ファイルになった。
