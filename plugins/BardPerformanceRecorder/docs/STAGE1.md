# 第1段階：取得可能性の検証結果

**検証日**：2026-09-20
**ゲーム**：`ffxiv_dx11.exe` ver `2026.09.15.0000.0000`（ファイル日付 2026-09-17）
**Dalamud**：`15.0.3.5-61-g5513cba33-estell.42`
**ImageBase**：`0x140000000`

## 結論

**他者の演奏の音符は、現在のゲーム・Dalamud でも観測できる。**
したがって第2段階以降（記録の土台・MIDI書き出し）に進んだ。

ただし **音の長さ（消音）はパケットに含まれない**ため、
出力される音長はすべて推定値である。

---

## 1. 検証のやり方

設計図の指示どおり「過去の構造体・シグネチャが現在も有効だと仮定しない」ため、
**ゲームを起動せずに実行ファイルを直接調べる**方法を取った。

1. `ffxiv_dx11.exe` の PE ヘッダを読み、`.text` セクションを特定
2. MidiBard2 の `Offsets.cs` にある各シグネチャを、マスク付きでバイト列検索
3. ヒットした関数を逆アセンブル（capstone）し、
   **引数の使われ方とデータ構造のオフセットを実際のコードから読み取る**

シグネチャが当たっただけでは「同じ関数」とは言い切れないため、
必ず逆アセンブルして中身が想定どおりかを確認した。

## 2. シグネチャの生存確認

| シグネチャ | 結果 | アドレス |
|---|---|---|
| `SoloReceivedHandler` | **一意にヒット** | `0x140B4E7F0` |
| `EnsembleReceivedHandler` | **一意にヒット** | `0x140B4E860` |
| `PerformanceStructPtr` | 一意にヒット | `0x140865000` |
| `DoPerformAction` | 一意にヒット | `0x141968F20` |
| `NetworkEnsembleStart` | 一意にヒット | `0x140D5E3D0` |
| `SoloSendHandler` | 一意にヒット | `0x14196C610` |
| `EnsembleSendHandler` | 一意にヒット | `0x14196C430` |
| `ChangeKeyboardLayout` | 一意にヒット | `0x140F7FE75` |
| `ChangeOctave` | **見つからない** | － |
| `SetOption` | **見つからない** | － |

`ChangeOctave` と `SetOption` は現行では通用しない。
ただしこの2つは**送信・操作側**のもので、記録には使わないため影響しない。

補強材料として、Solo と Ensemble の受信ハンドラは `0x70` しか離れていない
**隣接した兄弟関数**である。偶然同じバイト列に当たったのではない。

## 3. 逆アセンブルによる裏取り

### ソロ受信ハンドラ `0x140B4E7F0`

```asm
mov  rbx, rdx      ; 第2引数 = データポインタ
mov  edi, ecx      ; 第1引数 = 32bit の ID
```

旧定義 `IntPtr f(uint sourceId, IntPtr data)` と一致する。

実際にデータを読む内側の処理（`0x141967BF0`）：

```asm
movzx eax, byte ptr [rdi]           ; offset 0     = 音符数
cmp   al, 0Ah                       ;   上限 10
movzx eax, byte ptr [rcx+rdi+1]     ; offset 1..10  = 音符番号
movzx eax, byte ptr [rcx+rdi+0Bh]   ; offset 11..20 = 音色
```

→ **旧 `SoloPerformanceIpc` の定義は現在もそのまま有効**。

### 合奏受信ハンドラ `0x140B4E860`

```asm
mov r8, rdx / mov edx, ecx / jmp 0x1419689B0   ; 末尾呼び出し
```

内側（`0x1419689B0`）のループ：

```asm
lea   rdi, [r12+8]                  ; 演奏者配列は offset 8 から
mov   ebp, 8                        ; 8人分
sub   rdi, -80h                     ; 1人あたり 0x80 バイト
mov   eax, dword ptr [rdi]          ; +0x00 CharacterId（空き枠 0xE0000000）
movzx eax, byte ptr [rdi+4]         ; +0x04 音符数
cmp   al, 3Ch                       ;   上限 60
movzx eax, byte ptr [rdi+rcx+5]     ; +0x05 音符番号 ×60
movzx eax, byte ptr [rdi+rcx+41h]   ; +0x41 音色 ×60
```

→ 1人分 = 4+1+60+60 = 125 バイト、**パディング込みで 128 バイト**。
旧構造体の末尾 3 バイトのパディングと一致する。

### 楽器の取得

`Offsets.PerformanceStructPtr` は **自分のキャラクター専用**で、他人には使えない。
他人の楽器は FFXIVClientStructs の `Character` から読む：

| フィールド | オフセット | 内容 |
|---|---|---|
| `EntityId` | `0x78` | 受信ハンドラの `sourceId` と同じ 32bit ID |
| `Mode` | `0x2364` | `CharacterModes.Performance` = **16** なら演奏中 |
| `ModeParam` | `0x2365` | 演奏中のとき **Perform シートの行ID（＝楽器）** |

`CharacterModes` の値は、実際に導入されている
`FFXIVClientStructs.dll`（15.0.3.5）をリフレクションで読んで確認した。

なお FFXIVClientStructs には **演奏パケット関連の型は存在しない**
（`PerformanceModule` は自分の演奏設定の保存用であって、音符は持たない）。
そのため受信ハンドラのフックが唯一の手段になる。

## 4. 取得可否の一覧（設計図の要求項目）

| 項目 | 判定 | 根拠・注意 |
|---|---|---|
| 演奏者を識別できるID | **取得できた** | 受信ハンドラ第1引数の `sourceId`（= `EntityId`）。合奏時は枠ごとの `CharacterId` |
| 音符 | **取得できた** | ソロ offset 1〜10 / 合奏 各枠 +0x05〜 |
| 楽器 | **推定できる** | `Character.ModeParam`。受信時に別途読むため、**視界外・演奏モード外だと取れない**（その場合 -1 を記録） |
| 音色（トーン） | **取得できた** | ソロ offset 11〜20 / 合奏 各枠 +0x41〜。ギターの音色切替など |
| 音の開始時刻 | **推定できる** | 取れるのは **パケット受信時刻** のみ。演奏者が実際に弾いた時刻とは通信の遅れぶんずれる |
| 音の終了・長さ | **取得できない** | パケットに音長は無い。次のパケットで音が消えたことから推定するしかない |
| 合奏時の各演奏者の区別 | **取得できた** | 合奏パケットは演奏者ごとに 0x80 バイトの枠に分かれている |
| テンポ | **取得できない** | パケットに存在しない |
| 強弱（ベロシティ） | **取得できない** | パケットに存在しない |

### 番兵バイト

| 値 | 意味 |
|---|---|
| `0xFF` | 発音していない |
| `0xFE` | 直前の音を保持している（新規の発音ではない） |

この2つを発音として扱うと、存在しない音が大量に混ざる。

## 5. この検証の限界（未確認の点）

- ここまでは**すべて静的解析**であり、**実際にパケットが流れてくるところは未確認**。
  シグネチャが正しい関数を指していること、構造体のレイアウトが合っていることは
  確認したが、「実機で他人の演奏を記録できた」ことはまだ確認していない。
- `MidiNoteOffset = 48`（ゲームの音符 0 を MIDI の C3 に対応させる）は
  MidiBard2 の扱いに合わせた**仮の値**。実機での音高照合が必要。
- 実機検証の手順は README の「実機での検証手順」を参照。
